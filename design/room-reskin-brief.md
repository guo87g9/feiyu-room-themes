## 1. 二创定位

### 1.1 一句话定位（可直接用于 README 首屏）

> **本仓库是基于 `sh2234113/feiyu-room-template` 代码（MIT，保留原版权行）新建的独立公开仓库：保留上游 3D 陪伴房间的户型与全部玩法，只新增 4 套可切换的房间配色主题；它不是原创房间，不 Fork、不继承上游 git 历史，也不隶属于 DeepSeek、SnowLuma、腾讯或 QQ 官方。**

### 1.2 定位边界（三句话讲清"是什么 / 不是什么"）

- **是**：在已有房间代码上做「换装」——改材质配色、灯光氛围、窗外环境与装饰性几何的表达；代码取自上游模板并按 MIT 保留原版权行，仓库为独立新建、不继承其 git 历史。
- **不是**：不是从零生成的房子，不是新游戏，不是原创房间，不是上游作者的官方续作，也不是任何厂商的官方项目。
- **不含**：不含作者自制 3D 角色模型、不含第三方安装包、不含角色卡 / 私人记忆 / 聊天记录 / 账号与密钥等私人素材。

### 1.3 与上游「方式 A / 方式 B」的关系（防支柱漂移的关键判断）

上游 `README.md` 定义了两条路径：

- **方式 A**：直接复刻这套房子，代码 / 界面接近 1:1；
- **方式 B**：让 DSH 从零生成「你自己的房子」，`HOUSE_GENERATION_PROMPT.md` 里的 6 套风格方向是给方式 B 用的。

**本仓库属于方式 A 的视觉衍生版本，不属于方式 B。** 本 brief 的「海边小屋 / 森林木屋 / 中式小院」是**沿用上游已有的方向名**以降低认知成本，但语义已改变：它们不再是「另建一栋房」的生成提示词，而是「同一间房换一套皮肤」的主题配置。

> ⚠️ **一致性风险**：同名不同义。若 README 或 UI 把这 4 套写成「让 DSH 生成你自己的房子」，会与上游方式 B 混淆，并在实质上把「换皮」升级成「改户型」。文案必须显式写明「同一户型、只换配色」。
> ⚠️ **R6 措辞红线**：`INSPIRATION.md` 禁止把灵感来源写成「原创」，而 R6 又要求「非 Fork、独立新建仓库」。两者不矛盾——**代码来源必须写清（上游模板 + MIT 版权行），仓库建仓方式必须写清（独立新建、不继承 git 历史）**，缺任一句都会一边踩「原创」、一边踩「Fork 继承模型副本」。

## 2. 主题系统：4 套可切换主题

### 2.1 通用规则（先立契约，再谈审美）

**主题的作用域**

| 作用域 | 允许 | 禁止 |
| --- | --- | --- |
| 材质配色 | ✅ 墙 / 地 / 家具 / 软装的基色与粗糙度 | ❌ 改家具尺寸、位置、数量 |
| 灯光 | ✅ 色温、色调、渐变氛围 | ❌ 改光照强度基准到影响可读性的程度 |
| 窗外 / 天空 | ✅ 程序化渐变、剪影、雾感 | ❌ 引入外部图片 / CDN / 真实照片 |
| 装饰性几何 | ✅ 无碰撞、不可交互的点缀（窗格纹样、织物、小摆件） | ❌ 新增可点击物、新碰撞体、新寻路障碍 |
| 玩法数据 | — | ❌ 户型、房间状态机、寻路点、交互热区、菜园数值、聊天逻辑、角色动作表一律不动 |
| 角色 | — | ❌ 不替换、不重绘、不改 dsh-pet 2D 立绘与动画 |

**色彩语义锚点写法约定（本 brief 不写具体 hex）**

所有主题统一按三档语义描述；**具体色值已由 art-director 在 `design/asset-license-matrix.md` §3.2 / §3.3 定稿并写入主题配置表**，本 brief 只给语义锚点、不复写数值：

- **主色**：大面积底色（墙面 / 天花 / 地面基调），决定「这间房的第一印象」；必须低饱和、高留白，让 2D 立绘始终是视觉焦点。
- **辅色**：结构与家具色（柜体、窗框、地板、梁、软装主体），决定「家的秩序感」；与主色保持明度差，避免糊成一片。
- **点缀色**：小面积高识别色（把手、灯罩边缘、可点击高亮、交互反馈），**承担交互焦点职能**；4 套主题各只保留**一支**点缀色，禁止多支并列造成反馈语义不一致。

**命名与 key 约定**

| UI 中文名 | 配置 key | 是否默认 |
| --- | --- | --- |
| 蓝白小屋 | `blue_white` | ✅ 默认 |
| 海边小屋 | `seaside` | — |
| 森林木屋 | `forest` | — |
| 中式小院 | `courtyard` | — |

- UI 只显示中文名；代码 / 配置 / 持久化用英文 key，避免中文 key 带来的编码与迁移问题。
- 主题选择记在**浏览器本地**（与上游聊天记录同层的本地持久化），不写入服务端、不进入公开仓库、不需要账号。

**跨主题不变量（可访问性与性能）**

- 交互热区 / 可点击物在 4 套主题下保持**相同的对比度下限**；低照度主题不得让按钮「藏起来」。
- 4 套主题的几何体数量、draw call 与材质数量保持同一量级；不得出现「某套主题明显更卡」的性能主导策略。
- 昼夜切换逻辑对所有主题一致；主题只改变昼夜的**色调**，不改变昼夜的**判定与时长**。

**可访问性分级：Standard（依据 `design/asset-license-matrix.md` §4）**

- **结论**：本分支采用 **Standard**；不采用 Basic，也不承诺 Comprehensive。此句为 UX 规格与实现共用的显式引用，避免两侧各说各话。
- **为什么不是 Basic**：4 套可切换主题会让墙色、灯光与点缀色在套间漂移，天然带来对比度衰减与低照度风险（2.4 已把 T2 标为红线）。Basic 不要求系统性对比度门禁，无法覆盖「主题切换不得造成可读性劣势」这条核心红线。
- **为什么不是 Comprehensive**：角色动画是第三方 `webm` / `png`，**CC BY-NC-SA 4.0 的素材不可改**约束（美术 §2.1 / HC-1）使屏幕阅读器级的完整动作描述、音频描述与全量输入重映射无法在不改素材的前提下完整覆盖；且超出「精简合规版」定位。列为后续升级路线，不作为本轮承诺。
- **分级定义**：`Standard = WCAG 2.1 AA 基线 + 4 套主题逐套对比度门禁 + 动效 / 色觉 / 键盘可访问；不含屏幕阅读器全量适配与音频描述。`
- **落地口径（UX 与实现共用）**：
  1. HUD / 对话框 / 页脚的「文字色 + 面板底色」配对**不随主题变化**，主题只作用于 3D 场景，让「换皮」与「可读性」解耦；
  2. 正文 ≥ 4.5:1、大字 / 图标 / 交互热区 ≥ 3:1，**4 套 × 4 时段（day / dawn / dusk / night）共 16 种组合**逐一校验，取最小值作为门禁；
  3. 3D 房间标签与页脚署名必须自带底板，不依赖墙色（美术 §4.3 实测四套浅墙上白字仅约 1.1:1，属必修项而非优化项）；
  4. 2D 立绘只用**容器层**深色柔光 / 描边 / 底板兜底，禁止对素材施加色彩滤镜并导出；
  5. 状态不得只靠颜色编码（四套点缀色色相不同，此项更重要）；
  6. 夜间 + 森林木屋等暗组合**不得降低光照强度基准**来营造氛围。
- **依赖状态**：可访问性分级 **Standard**（美术 §4）与 T2 墙色折衷（美术 §6 R-2）均按**已决口径**执行——Standard 已定案，R-2 经设计侧会签通过即生效，无需用户再拍板；本文档全篇按已决口径落笔，不留未决钩子。

### 2.2 T0 · 蓝白小屋（默认）

- **3 个风格词**：清爽 · 通透 · 治愈
- **语义锚点**
  - 主色：**低饱和浅冷白**（"干净的画布"）——大面积墙面与天花，压低饱和度，把视觉焦点让给蓝发立绘。
  - 辅色：**藏青**（"稳定与秩序"）——柜体、窗框、结构线、软装主体，直接呼应立绘裙装的深蓝。
  - 点缀色：**白金 / 暖金**（"少量贵金属光泽"）——把手、灯罩边缘、交互高亮，呼应立绘白金饰边与鲸尾的高光。
- **光 / 材质 / 窗外**：高漫反射、低金属、柔和匀光；白天偏冷白，夜晚偏暖但强度基准不变；窗外用程序化的远海平线与浅雾渐变，不用图片。
- **与 dsh-pet 立绘的呼应逻辑（设为默认的理由）**：立绘是蓝发 + 藏青白金裙装 + 鲸尾的冷色系角色。默认主题取「冷白底 + 藏青结构 + 白金点」正好构成角色配色的环境放大版，角色站在房间里不跳色、不抢色，陪伴感最强。**明确禁止**使用高饱和亮蓝做主色——那会与蓝发糊在一起，削弱角色识别度。
- **氛围一句话**：像刚晒过太阳的浅色被单，安静、干净、不打扰。

### 2.3 T1 · 海边小屋

- **3 个风格词**：明亮 · 松弛 · 自然
- **语义锚点**
  - 主色：**日晒暖白**（略带暖调的白，与 T0 的冷白形成可辨识区分）。
  - 辅色：**漂白原木**（可见木纹的浅木色，地板与家具结构），语义是「被海风吹旧的木头」。
  - 点缀色：**海玻璃青**（窗框、玻璃反光、交互高亮），语义是「捡到的海玻璃」。
- **光 / 材质 / 窗外**：强漫射、薄纱柔化感；窗外近海与沙色的程序化渐变；材质上允许更明显的木纹与织物粗糙感。
- **空间表达边界**：不新建落地窗、不扩阳台、不改窗洞几何。「海」只存在于窗外渐变与材质语气里。
- **与 T0 / T2 的区分度检查**：T0 是「冷白 + 素面 + 藏青」，T1 是「暖白 + 漂白木 + 海玻璃青」，T2 是「亚麻米 + 深木棕 + 炉火橙」。T0 与 T1 靠色相 + 明度双重可辨；**T1 与 T2 的主色同属暖白系，区分主要依赖辅色木作的明度差与点缀色色相（青 ↔ 橙）**，请 art-director 在 §4.3 逐套校验中一并覆盖这一组。若只差一点白，视为验收不通过。

### 2.4 T2 · 森林木屋

- **3 个风格词**：温暖 · 包裹 · 沉静
- **语义锚点（✅ 已与 art-director 会签（2026-11-15），依据 `design/asset-license-matrix.md` §2.4 / §6 R-2）**
  - 主色：**亚麻米 / 浅暖白**（墙与天花）——保持低饱和、高留白，让 2D 蓝发立绘始终是视觉焦点；与 2.1 的主色定义一致。
  - 辅色：**深木棕**（大面积木作、梁、深柜、地板与踢脚线，承担「被木头包住」的包裹感）+ **苔绿 / 灰绿**（织物、地毯、软装，语义是「窗外树影落进屋里」）。深木棕归位到结构 / 家具色，正是 2.1 对辅色的定义。
  - 点缀色：**炉火橙**（只做交互焦点与灯光色温的高光，语义是「屋里唯一的热源」），仍为本套唯一一支点缀色。
- **光 / 材质 / 窗外**：暖黄色温、材质偏粗糙低反射；窗外树影用程序化剪影；**不降低任何光照强度基准**（与 2.1 跨主题不变量、美术 §3.3 / §3.7 一致）。
- **空间表达边界**：不砌壁炉、不加阁楼、不新增实体家具；「壁炉感」只由辅色木作、点缀色与灯光色调表达。
- ✅ **会签结论（设计侧）**：美术的折衷与本文档设计意图**一致**。本文档原把「深木棕」写在主色位，与 2.1「主色必须低饱和高留白」及本节自身的低照度红线冲突；折衷把浅暖白留给墙 / 天花、把深木棕归位辅色 / 结构色，恰好修正了这一层级错配，同时保住「温暖 · 包裹 · 沉静」的氛围。按 brief 自身「不写具体 hex」的约定，此处只给语义措辞，**色值以 `design/asset-license-matrix.md` §3.2 / §3.3 为准**；**本会签通过即生效**，R-2 按已决口径执行，无需用户再拍板，本文档不留未决钩子。
- ⚠️ **设计红线标注（低照度风险）**：折衷后墙面为浅色，红线主因转为「夜间 + 森林木屋」的暗组合与深木作背景。仍须按 Standard 门禁校验：交互热区 ≥ 3:1、白字标签加底板、光照强度基准不随主题下调，避免玩家因「看不清」而被迫只选亮主题（视觉主导策略）。

### 2.5 T3 · 中式小院

- **3 个风格词**：素雅 · 秩序 · 留白
- **语义锚点**
  - 主色：**粉墙 / 宣纸白**（大面积留白），语义是「纸面」。
  - 辅色：**青砖灰 + 深木**（木格窗、结构线、家具），语义是「框与界」。
  - 点缀色：**朱砂**（只保留这一支，用于门扣、灯罩边缘、交互高亮），语义是「一点人间烟火」。竹影 / 竹青只作为窗外剪影存在，不参与交互反馈。
- **光 / 材质 / 窗外**：柔和中性光；窗外竹影为程序化剪影；几何上强调「格与框」的直线秩序。
- **空间表达边界（本套最关键）**：**「小院」是氛围，不是户型改造。** 不新增庭院、不铺石径、不改门洞、不加院墙——任何把「小院」实体化的做法都会改碰撞体与寻路，直接违反「换皮不改玩法」。可复用的是上游已有的**屋后菜园**：菜畦本就自带「耕作 / 庭院」的生活感，用主题语气把它接住即可。
- ⚠️ **一致性标注**：主题名含「院」而户型是大平层，文案上必须写清「取小院之意，不取小院之形」，避免用户预期落差。

### 2.6 主题契约汇总

| 契约 | 内容 |
| --- | --- |

## 3. 体验支柱与 MDA

### 3.1 三条设计支柱

| # | 支柱 | 含义 | 违反它的样子 |
| --- | --- | --- | --- |
| **P1** | **同一间房，四种天气** | 家是恒定的，情绪是可换的；陪伴对象不因换装而改变，角色站在哪、能做什么、记得什么全部照旧 | 换主题后角色换人、家具挪位、菜园重置 |
| **P2** | **零学习成本** | 切换只有一个按钮，不引入新操作、新数值、新位置记忆；换装是放松，不是考试 | 主题带解锁条件、带数值加成、带教程弹窗 |
| **P3** | **可溯源、可复刻** | 所有视觉差异收敛到一张公开的主题配置表，任何人都能看懂来源、改一行加第 5 套 | 颜色散落在多个文件里硬编码，无法解释「这套主题是什么」 |

> P3 同时是**开源独立仓库定位**的设计表达：这个仓库的价值不是「我做了个新房间」，而是「我把换装这件事做成了一张可读的表」；代码来源与上游 MIT 版权行仍完整保留，不因新建仓库而隐去。

### 3.2 MDA 简表

| 层 | 内容 |
| --- | --- |
| **M · 机制（规则 / 数据）** | 一张 4 组参数的主题配置表（主 / 辅 / 点缀色语义、灯光色调、窗外渐变、装饰几何开关）；一键切换；选择本地持久化。**玩法侧状态机、寻路、菜园数值、聊天逻辑完全不变。** |
| **D · 动态（运行时行为）** | 玩家按心情 / 时段 / 季节换装；并排比较 4 套差异；截图分享；给陪伴角色"配一套背景"。因为切换**没有任何数值收益**，不会产生「刷最优主题」的功利行为，也不会出现主导策略——玩家的选择纯粹是审美偏好。 |
| **A · 美感（目标体验）** | 清爽、松弛、温暖、素雅四种「家」的语气；核心情绪是**陪伴感与可久待**，不是拟真、不是探索压力、不是收集焦虑。 |

### 3.3 「换皮不改玩法」为什么成立（论证）

1. **形式论证**：玩法由「房间状态机 + 碰撞体 + 数值表 + 交互热区」定义；主题配置表只向渲染层提供**材质与灯光参数**。二者是单向的读取关系，主题表不写回任何玩法状态，因此 M 层不产生新规则，D 层不产生新策略，A 层的变化恰好就是设计目标。
2. **技术锚点（已抽查代码）**：`public/room/world.js` 已有集中的 `mat()` / `metal()` 材质构造函数，`garden-world.js` 也有集中的 `material()` 工厂——说明**把颜色参数抽成一张主题表在工程上是可达的**。现状颜色常量仍散落在多处（含天空渐变、菜园粒子等），需要 engineering-lead 做一次「散落硬编码 → 主题配置表」的收敛；这是 T-03 的实现要点，本 brief 只提出约束、不指定实现。美术另发现 `updateEnvironment()` 会覆写主题色、以及不经 `M` 对象的硬编码色盲区，见 `asset-license-matrix.md` HC-4 / HC-5。
3. **反向边界（ falsification 条件）**：只要出现以下任一情况，「换皮」即告失效，必须重新评审——
   - 主题改动了家具尺寸 / 位置 / 碰撞体；
   - 主题影响了交互热区对比度或帧率；
   - 主题携带了任何玩法数值或解锁条件；
   - 主题引入新的 3D 资产或外部图片。
4. **玩家心理映射**
   - **自我决定论 · 自主性**：4 套主题提供「我的房间我做主」的低风险选择；不增加**胜任**负荷（没有新操作要学），不引入**归属**压力（不要求分享 / 排名）。
   - **Bartle**：主要服务**探索型**（对比 4 套细节、想加第 5 套）与**社交型**（截图分享）；刻意不服务成就型 / 杀戮型，所以不做进度、成就、排行榜、数值加成——这正是 P2 的理论依据。
5. **认知负荷**：4 套是**可一次性扫完**的数量级；超过 4 套或让每套附带子选项，会滑向认知过载。按 R5 决议（2026-11-15）本分支锁死 4 套，「加第 5 套」不进本分支范围。

### 已知取舍

- **取舍 1**：为了让「换皮不改玩法」在技术与合规上同时成立，本分支已放弃「中式小院」的空间实体化（院落 / 石径 / 竹影实体），只保留氛围表达。视觉震撼度下降，换来户型零改动与授权零风险。
- **取舍 2**：默认主题定为冷色系「蓝白小屋」，与上游「奶油 + 橡木 + 藏青」的暖色基调不同，这是**有意的差异化**。按 R5 决议主题数锁死 4 套，上游暖色基调不作为隐藏「原味」主题引入。
- **取舍 3**：移除自制 3D 模型后，房间的「拟真度」下降，陪伴感更多由 2D 立绘与氛围承担。这与支柱 P1「陪伴感优先于拟真」一致；相关的预期说明已写入 5.2 与 5.4，避免用户按上游截图预期落空。
- **取舍 4（会签追加）**：T2 森林木屋放弃「墙也刷深木棕」的暗房方案，改由浅暖白墙 + 深木棕结构色表达包裹感。视觉上的「暗房沉浸感」下降，换来 2D 立绘辨识度、文字对比度与低照度红线的同时满足，是 Standard 分级下的必要取舍。
- **取舍 5（R6 追加）**：新建独立仓库意味着放弃上游的 commit 历史、issue / PR 联动与自动归因，换来 58.9 MB / 6.7 MB GLB 历史对象的**彻底清零**——这是「砍掉作者 3D 模型」在 git 层面的唯一完整解。代价是必须在 README 与 5.4 里主动写清代码来源与 MIT 版权行，否则容易被误读成「原创」（`INSPIRATION.md` 红线）。

### 边缘情况（设计层，至少 3 类）

1. **切换时机**：角色正在走路 / 吃饭 / 睡觉、菜园正在浇水结算、电视正在投屏时切换主题 —— 应只换渲染参数，动画状态机、结算事务、投屏流不得中断或重置。
2. **持久化异常**：本地存储被清空 / 隐私模式 / 跨浏览器打开 —— 必须回落到默认 `blue_white`，不得白屏、不得报错、不得静默套用上一套残留值。
3. **未知 / 非法 key**：配置或 URL 里出现第 5 套或拼写错误的 key —— 回落到默认主题并保留一次可诊断提示，不做猜测式匹配。
4. **主题与昼夜叠加**：夜间 + 森林木屋（最暗组合）、正午 + 海边小屋（最亮组合）—— 两极端都需满足交互热区对比度下限，光照强度基准不随主题漂移；按 Standard 的 16 组合门禁逐一留证。
5. **下游再分发 / 二次发布**：下游若再加主题或改色，仍须保留 `INSPIRATION.md`、MIT 版权行与 dsh-pet 署名，遵守 R7 纯非商业，且不得把上游 git 历史（含 glb 对象）重新引入；5.4 段落为 README 中的「不可删段落」。
